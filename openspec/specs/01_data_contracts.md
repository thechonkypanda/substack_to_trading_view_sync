# Spec 01: Data Contracts & Ingestion Schemas

## 1. Overview
This specification defines the input schemas and contracts for data ingested directly via APIs:
1. **Google Sheets API**: Retrieves form responses (timestamps, emails, TradingView usernames).
2. **Substack Creator API**: Retrieves active paid subscribers (emails, membership state, subscription type, expiry).
3. **TradingView Access List**: Retrieves current invite-only indicator permissions.

---

## 2. Google Sheets Ingestion Contract

### 2.1 API Ingestion Method
- **Client**: Google Sheets API v4 (or authenticated service account client).
- **Target**: Specified by `GOOGLE_SHEET_ID` and sheet range.

### 2.2 Response Row Structure

| Column Index | Field Name | Type | Description |
| :---: | :--- | :--- | :--- |
| `0` | `submitted_at` | ISO-8601 / Datetime string | Timestamp when form was submitted (auto-generated by Google Forms). |
| `1` | `email` | String (Email) | Substack account email. |
| `2` | `tradingview_username` | String | TradingView handle. |

### 2.3 Field Validation Rules
- **`email`**: Must be non-empty, trimmed of whitespace, lowercased, and match valid email format (`^[^@\s]+@[^@\s]+\.[^@\s]+$`).
- **`tradingview_username`**: Must be non-empty, trimmed of whitespace, alphanumeric (plus underscores/hyphens). Any leading `@` is automatically stripped.

## 3. Substack Ingestion Contract

### 3.1 Direct Substack API Endpoint
* **Endpoint**: `GET https://{SUBSTACK_SUBDOMAIN}.substack.com/api/v1/subscribers`
* **Query Parameters**:
  * `filter`: `paid`
  * `limit`: `100` (paginated via `offset` or `page`)
  * `order_by`: `created_at`
  * `sort_direction`: `desc`
* **Headers**:
  * `Cookie`: `substack.sid={SUBSTACK_SESSION_COOKIE}`
  * `User-Agent`: Standard browser User-Agent

### 3.2 Response Schema (JSON)
```json
[
  {
    "id": 1234567,
    "email": "subscriber@example.com",
    "membership_state": "active",
    "subscription_type": "paid",
    "status": "active",
    "expiry": null,
    "created_at": "2026-01-15T12:00:00.000Z"
  }
]
```

### 3.3 Paid Qualification Rules
A subscriber record is classified as **Paid Active** if:
1. `email` is present and valid.
2. `subscription_type` (case-insensitive) is one of: `["paid", "comp", "founding", "gift"]`.
3. `status` or `membership_state` is NOT in `["canceled", "expired", "inactive", "refunded"]` (unless `expiry` is set to a future timestamp).

## 4. TradingView Authorized State Schema

### 4.1 Concept & Purpose
When a Pine Script indicator is published as **Invite-Only**, TradingView maintains a private access list. The sync engine queries this list to determine who currently holds access, preventing duplicate grants and identifying which former subscribers need access revoked.

### 4.2 Raw TradingView API Response
TradingView's internal permissions endpoint returns a JSON payload of invited users:

```json
{
  "status": "ok",
  "users": [
    {
      "username": "trader_alice",
      "user_id": 987654,
      "expiration": null
    },
    {
      "username": "bob_macro",
      "user_id": 876543,
      "expiration": "2026-12-31T23:59:59Z"
    }
  ]
}
```

### 4.3 Normalized Internal State Model
The sync engine normalizes TradingView records into the following Python dataclass / JSON representation:

```json
{
  "username": "trader_alice",
  "user_id": 987654,
  "expiration": null,
  "has_access": true
}
```

| Field | Type | Description |
| :--- | :--- | :--- |
| `username` | String | Canonical TradingView username (case-insensitive comparison). |
| `user_id` | Integer / null | TradingView internal account ID. |
| `expiration` | String / null | `null` for indefinite/ongoing access; ISO-8601 datetime for fixed-term access. |
| `has_access` | Boolean | `true` if active in the script's authorized user list. |
